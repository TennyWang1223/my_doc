# AllGather + GEMM 融合算子 — 计算模型与分块结构笔记

> 环境:8× AMD MI300X(gfx942 / CDNA3),单节点。代码:`amd-distributed/all-gather-gemm/ref10_first.py`,比赛第 1 名实现。
> 本篇专注**计算模型 + block/tile 分块结构**,和另一篇 `ag-gemm-学习笔记.md`(偏 cache 层级 / 通信硬件通路)互补。
> 贯穿全篇的具体形状:`Mi=512, M=4096, N=512, K=4096`,config `BLOCK_M=64, BLOCK_N=64, BLOCK_K=256, SPLIT_BLOCK=4, SEND_CTA_NUM=8`(对应 `online_config` 的 `(4096,512,4096)`)。

## 0. 最基础的计算模型(先钉死这个,别的都好懂)

**每张卡 = 一个独立的小 GEMM**,手里就三样本地完整张量,**不带"我是全局几分之一"的含义**:

```
input   [Mi, K]   ← 本卡自己的输入行
weight  [N,  K]   ← 本卡自己的权重,就叫 N,一个完整独立的东西
bias    [N]       ← 可选
```

kernel 干两件事:
```
1. 通信:把 8 张卡的 input 行凑齐 →  full_input [8·Mi, K]     (记 M = 8·Mi)
2. 计算:output = full_input @ weight.T  →  [M, N]
```

### 唯一有"跨卡结构"的维度是 M

| 维度 | 在 kernel 里的含义 | 要不要联想"8 个 rank" |
|---|---|---|
| **M** | `8·Mi`,输入行,由 allgather 凑齐 | **要**——天生 8 段拼成,通信/等 flag 全围绕它 |
| **N** | 本卡权重行数,一个数 | **不要**——就是个本地尺寸 |
| **K** | 收缩维(reduction,累加方向) | **不要**——本地尺寸 |

> ⚠️ **不要用 `n/8` 的全局 TP 视角讲这个 kernel**。那个 `/8` 只是测试脚本按全局 `n` 参数化再切给每卡的账,对理解算子本身是弯路。每卡的 N 就是本地权重行数,一个完整独立的数,句号。

## 1. 通信模型:push + 本地读,只有 input 走网络

```
   full_input [M=4096, K]                weight [N=512, K]       output [M=4096, N=512]
 ┌──────────────────────┐              ┌────────────────┐       ┌────────────────┐
 │ rank0 的 512 行 ◄本地 │              │                │       │  用 rank0 输入  │
 ├──────────────────────┤              │   本卡 weight   │       ├────────────────┤
 │ rank1 的 512 行 ◄网络 │              │   立在这儿      │       │  用 rank1 输入  │
 ├──────────────────────┤     ×        │   本地读        │   =   ├────────────────┤
 │ rank2 的 512 行 ◄网络 │              │   全程不动      │       │  用 rank2 输入  │
 │        ...           │              │                │       │      ...       │
 ├──────────────────────┤              │                │       ├────────────────┤
 │ rank7 的 512 行 ◄网络 │              │                │       │  用 rank7 输入  │
 └──────────────────────┘              └────────────────┘       └────────────────┘
   ▲ 唯一跨卡的维度 M                      ▲ N、K 只是本地尺寸       ▲ rank0 只产出这一块
   =8段拼,1段本地7段等网络                                          (别的 rank 算别的 output)
```

- **横向流动(通信)的只有 input 行**:8 个 rank 各把自己的 `Mi` 行 push 给别人,凑成 `M=8·Mi` 行。
- **weight 竖着立着不动**:本卡用自己这 N 行 weight,全程本地 cached 读。**weight 一个字节都不过网络。**
- **为什么 weight 不用通信**:正因为各卡 weight 独立、互不关联,天然分好了,谁也不需要别人的 weight。
- **为什么 input 要通信**:每卡只有 `Mi` 行 input,但算输出需要全部 `M` 行(输出每一列都要和所有输入行相乘),所以必须 allgather。
- **一句话**:input 行不够 → 要通信凑齐;weight 列各管各的 → 不用通信。

**push + 本地读**:rank0 主动把 input0 **写穿(write-through)**到其他 7 卡显存,同时接收别人 push 来的 input1..7 落进自己的 full_input。所以 rank0 的 full_input 第 0 段本地现成,第 1~7 段等别人写进来。只有"写"穿越网络,"读"永远本地。

## 2. 一个 kernel 里所有 block 的分工

一个常驻(persistent)Triton kernel,grid 一维铺开,按 `program_id` 分两类,用 `COMM_PIDs = 7 * SEND_CTA_NUM` 划界:

```
 program_id:  0 ─────────────► 55 │ 56 ──────────────────────────────► 567
             ┌───────────────────┼──────────────────────────────────────┐
             │   通信 CTA  56 个   │           计算 CTA  512 个             │
             │  = 7 × SEND_CTA(8) │  = grid_m(64) × grid_n(8)            │
             └───────────────────┴──────────────────────────────────────┘
              把 input0 推给 7 卡      每个算一个 64×64 输出格子
              (每目标卡派 8 个 CTA)    (id 小的先被硬件发射)
```

> CTA(Cooperative Thread Array)= 一个线程块 = 一个 block。

**为什么"先算本地后算远端"能成立(虽然 block 并发)**:
- block 不是全部真并发,受 occupancy(占用率)限制,一批批发射。
- CDNA 硬件调度器**大致按 program_id 递增发射**(不是标准保证,但实测很稳)。
- 布局故意排成:通信 CTA(id 最小,最先上,立刻推数)→ 本地计算(不等 flag,直接算)→ 远端计算(id 最大,最后上,那时数据多半到了)。
- **正确性不靠这个顺序**,靠 flag 自旋兜底(见 §5);顺序只是"软倾向",用来凑 overlap。

## 3. 计算侧的分块:三个层次别混

GEMM 把大输出矩阵切成**二维小格子**,一个 block 算一个格子。以 rank0 的一个输出条带(一个 rank 的段)为例:

| 层次 | 行 | 列 | 说明 |
|---|---|---|---|
| **数据**(元素) | 512 | 512 | `Mi=512` 输入行,`N=512` weight 列 |
| **tile**(格子数) | 8 | 8 | 512/64=8,共 8×8 = **64 个 block** |
| **单个 block** | 64 | 64 | `BLOCK_M × BLOCK_N` |

整个输出 `[M=4096, N=512]`:
- `grid_m = M/BLOCK_M = 64` 个行 tile
- `grid_n = N/BLOCK_N = 8` 个列 tile
- 共 `64 × 8 = 512` 个计算 block

```
                    N=512 → grid_n=8 个列tile (BLOCK_N=64)
                col0  col1  col2  col3  col4  col5  col6  col7
              ┌─────┬─────┬─────┬─────┬─────┬─────┬─────┬─────┐
  行tile 0    │  ▢  │  ▢  │  ▢  │  ▢  │  ▢  │  ▢  │  ▢  │  ▢  │ ┐ rank0 段
  行tile 1..6 │     512行×512列 数据,  8×8 = 64 个 block          │ │ IS_LOCAL
  行tile 7    │  ▢  │  ▢  │  ▢  │  ▢  │  ▢  │  ▢  │  ▢  │  ▢  │ ┘ 直接读,不等
              ├─────┼─────┼─────┼─────┼─────┼─────┼─────┼─────┤
  行tile 8    │  ▢  │  ▢  │  ▢  │  ▢  │  ▢  │  ▢  │  ▢  │  ▢  │ ┐ rank1 段
  行tile 9..14│             ... 又 64 个 block ...               │ │ 等 rank1 flag
  行tile15    │  ▢  │  ▢  │  ▢  │  ▢  │  ▢  │  ▢  │  ▢  │  ▢  │ ┘
              ├─────┼─── rank2~6 段, 每段 8 行tile ──────────────┤
  行tile56..63│             rank7 段, 64 个 block               │
              └─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┘
```

- **一个 block 读什么**:`A` = 对应的 64 个输入行(可能等网络) + `B` = 对应的 64 列 weight(本地),沿 K 累加 `acc += A×B`。等 flag 只卡在 A 上,B 永远现成。
- `IS_LOCAL = (pid_m // (grid_m//8)) == my_rank`(`ref10_first.py:980`):看这个 tile 的行属于哪个 rank。
- 属于本卡的行 tile(0~7)直接读;属于别的 rank 的(8~63)等对应 flag。

### 通信 8 vs 计算 64:两种不同的计数

| | 一个 rank 对应几个 block | 由什么决定 |
|---|---|---|
| **通信** | **8** 个 CTA | `SEND_CTA_NUM=8`,是**调参旋钮**——"派几个搬运工搬这份数据" |
| **计算** | **64** 个 block | 输出条带 tile 数 `8行×8列`——由**输出形状 + BLOCK_M/N** 硬算,不是旋钮 |

一个是"搬运并行度"(可调),一个是"输出格子数"(形状定死),维度不同,数不一样很正常。

## 4. 两把尺子:同一批输入行,两种独立切法

**某个 rank 的 512 输入行,被两把互不相干的尺子量:**

```
  rank1 的 512 行输入(由 rank1 push 到 rank0 显存)
  row0                                                              row511
 ──┼──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────────────┤
尺A│ t8   │ t9   │ t10  │ t11  │ t12  │ t13  │ t14  │ t15          │ 计算尺
计算│(64行)│(64行)│(64行)│(64行)│(64行)│(64行)│(64行)│(64行)        │ 8个行tile
 ──┼─────────────────────────────┬────────────────────────────────┤ 决定"谁来算"
尺B│      chunk 0 (256行)         │       chunk 1 (256行)          │ 通信尺
通信│  盖住 t8,t9,t10,t11          │  盖住 t12,t13,t14,t15          │ 2片(SPLIT_BLOCK=4)
 ──┴─────────────────────────────┴────────────────────────────────┘ 决定"分几次到/几盏灯"
        搬完→flag[rank1][0]=8            搬完→flag[rank1][1]=8
              │                                │
        t8~t11 等这盏                    t12~t15 等这盏
```

- **计算尺**:切 8 个行 tile(各 64 行),决定"哪个 block 算哪 64 行"。粒度 = `BLOCK_M`。
- **通信尺**:切 2 片(各 256 行),决定"数据分几次搬、亮几盏灯"。粒度 = `BLOCK_M × SPLIT_BLOCK`。
- 两把尺量的是**同一批 512 行**,但目的完全不同、互不冲突。类比:一个班 40 人,按座位分 8 排(计算)、按性别分 2 组(通信),同一批人两种分法不矛盾。

## 5. SPLIT_SEND / SPLIT_BLOCK 详解

| 参数 | 类型 | 是什么 | 大白话 |
|---|---|---|---|
| **SPLIT_SEND** | 开关 | `= (M >= 2048)` | "数据要不要分几次搬?" M 大就分,M 小一次搬完 |
| **SPLIT_BLOCK** | 数字 | 每片装几个 `BLOCK_M` | 片长 = `BLOCK_M × SPLIT_BLOCK` 行 |

本例:`SPLIT_SEND=True`(M=4096≥2048),`SPLIT_BLOCK=4` → 每片 `64×4=256` 行 → `Mi/256 = 2` 片。

**flag 为什么判 `!= SEND_CTA_NUM`(=8)**:一片由 8 个通信 CTA 协作搬,各搬完自己那份就 `atomic_add(+1)`。flag 累加到 8 ⟺ 这 256 行全落地。接收侧 `while result != 8` 自旋等待(`ref10_first.py:1000`)。

**接收侧算"我这个 tile 等哪盏灯"**(`ref10_first.py:991`):
```python
灯号 = (pid_m % (grid_m//8)) // SPLIT_BLOCK   # 本rank内tile序号 // 4
# t8→序号0→0//4=0→灯0    t12→序号4→4//4=1→灯1
```

### 为什么切成"4 个 tile 一片",不是每 tile 一盏灯?(核心权衡)

直觉:"切细点 `SPLIT_BLOCK=1`,每 tile 一盏灯,tile 0 数据一到就先算,overlap 更好?" —— **方向对,但切太细反而更差**,三个原因:

**① 搬运是"交错流式"的,本来就没法让某个 tile 先完成**
8 个通信 CTA 搬一片时是**跳着分工**(CTA0 搬第 0,8,16… 份,CTA1 搬第 1,9,17…),均摊在整片 256 行上。一片内部不存在"前 64 行先搬完",256 行一起零散填满、最后同时亮灯。想"tile 0 先亮灯"就得改成"先完整搬 tile0 再搬 tile1",把一大块顺序流量拆成 8 小段 → 踩下一条坑。

**② XGMI 喜欢大块顺序流量,切碎了掉带宽**
```
SPLIT_BLOCK=4 (256行/片,2片): [═══ 大块 ═══][═══ 大块 ═══]   带宽高
SPLIT_BLOCK=1 (64行/片,8片):  [块][块][块][块][块][块][块][块]  8盏灯,块小,带宽掉+同步开销涨
```
灯越多 = 同步点越多(每盏灯前 8 个 CTA 碰头一次,atomic 有争抢)+ 搬运被打断。省下的"早开算"不够赔进去的带宽/同步。

**③ 本地段的活已经够填满等待,不需要切太细**
rank0 自己那 8 个行 tile(64 个 block)是本地的,不等灯立刻算。计算 CTA 先埋头算这 64 个本地 block,**这段时间通信早把 chunk 搬来了**。等本地算完,远端已就位——不需要把远端切 8 份抢那几微秒。

**两个极端都不行:**
```
SPLIT_BLOCK=8 (1盏灯)  ── 太粗:远端全等到齐才动,overlap不足
SPLIT_BLOCK=4 (2盏灯)  ── 甜点:够重叠 + 大块流量 + 灯少   ← 本shape选这个
SPLIT_BLOCK=1 (8盏灯)  ── 太细:块碎掉带宽 + 同步开销 > 早开算收益
```
`SPLIT_BLOCK` 的值是**离线 autotune 搜出来的甜点**(别的 shape 表里是 2)。

### overlap 时间轴

```
时间 ──────────────────────────────────────────────────────────►
通信CTA: [推 rank1 chunk0] flag[1][0] [推 rank1 chunk1] flag[1][1]
计算CTA: [先算 rank0 本地段 t0~t7,不等任何灯]
                          └► t8~t11 开算(此时 chunk1 还在飞,被藏住)
                                       └► t12~t15 开算
```

## 6. autotune 是 Triton 特性吗?HIP 写 GEMM 要每个 shape 自己 tune 吗?

- **autotune 是 Triton 的封装**(`triton.autotune` 装饰器):给一堆候选 config,运行时实测挑最快的。本质就是"把手动 sweep 自动化"。
- **本冠军代码没在运行时用 autotune**:当**离线工具**用,赛前搜好、把赢家**硬编码进 `online_config`**(`ref10_first.py:1109`),运行时只查表(动态搜首次要预热,现场太慢)。

**如果用 HIP 手写 GEMM:**

| 路线 | 要不要自己 tune 每个 shape |
|---|---|
| **纯手写 HIP kernel** | 要。自己写 sweep 脚本或凭经验调,每类 shape 存一套参数(就像 `online_config`) |
| **rocBLAS / hipBLASLt** | 不用手 tune。库内部 heuristic + 预置 tuned 实例,给 shape 自动挑;hipBLASLt 还能 offline tuning |
| **Composable Kernel (CK)** | 介于两者:大量预生成 instance,你用它的 selection 或自己 profile 选 |

**一句话**:per-shape tuning 逃不掉(最优分块本来就随 shape 变),区别只是**谁来 tune**。本方案自己 autotune + 写死表,是因为要压榨**融合专属参数**(`SPLIT_BLOCK`、`SLEEP_CYCLE`)——这些 BLAS 库根本没有。

## 7. 测试 shape 总结

**重要**:`run.py` 的测试 config 和 `online_config`(融合支持表)**基本是两套**。融合真正支持的 shape 由 `online_config` 决定。

### A. 融合内核实际支持的 shape(`online_config`,key `(M,N,K)` → 原始 `(m, n=N×8, k)`)

| key (M, N, K) | 原始 (m, n, k) | BLOCK_M/N/K | SPLIT_BLOCK | 路径 |
|---|---|---|---|---|
| (512, 1536, 4096) | (512, 12288, 4096) | 64/64/256 | 2 | 融合 |
| (2048, 360, 2880) | (2048, 2880, 2880) | 64/32/128 | 2 | 融合 |
| (4096, 512, 4096) | (4096, 4096, 4096) | 64/64/256 | 4 | 融合 |
| (8192, 1792, 4096) | (8192, 14336, 4096) | 256/128/64 | 2 | 融合 |
| (8192, 3696, 8192) | (8192, 29568, 8192) | 256/256/64 | 2 | 融合 |
| (64, 2304, 7168) | (64, 18432, 7168) | 空 `{}` | — | **死条目**,实际走 split-k |

> 最后一行是死条目:`m=64 且 k=7168` 会先被 `custom_kernel` 开头的 `if local_M==8 and K==7168` 拦去 split-k 路径(`ref10_first.py:1145`),到不了查表。

### B. 特殊/兜底路径

- **split-k 融合**:`m=64 且 k=7168`(`launch_triton_split_k`,`ref10_first.py:1496`)。M 太小(每卡 8 行),改成沿 K 切 8 份并行 + reduce。它每个计算 block 反而是 `for rank in range(8)` 等全部 8 个 rank(和主融合不同)。
- **fallback**:其余所有 shape → `origin()`(`ref10_first.py:1297`),老实的 `all_gather + torch.matmul`,不融合。

### C. run.py 里实际触发融合的(dispatch 见 §7.A/B)

run.py 定义 18 组,`_worker` 只跑 `config[:5]`。逐一映射后:
- **命中融合**只有 2 组,且都不在前 5(默认跑法其实测不到融合路径):
  - `(2048, 2880, 2880)` → key `(2048,360,2880)` ✓
  - `(4096, 4096, 4096)` → key `(4096,512,4096)` ✓
- 前 5 组全 fallback(一组纯正确性校验,专挑小/边角 shape)。

## 8. 关键纠错记录(避免下次重犯)

| 误区 | 纠正 |
|---|---|
| "weight 也要参与通信" | ❌ 只有 input 行走网络,weight 全程本地静止 |
| "用 n/8 全局 TP 视角理解 kernel" | ❌ 弯路。每卡 N 就是本地权重行数,一个完整独立的数 |
| "每卡输出是 `[8m, n]`" | 每卡输出是 `[M, N]`,只产出本卡这 N 列(别的 rank 算别的列) |
| "8 个 block 算一个 rank" | 是 8 个**行 tile**,但每行 tile 还有 8 列 → 一个 rank 由 **64 个 block** 算 |
| "计算 block 先算本地再循环算 7 次远端" | ❌ 一个 block 只算一个 tile。本地/远端是**不同 block 空间分工**,不是单 block 时间循环 |
| "通信切细(每 tile 一盏灯)overlap 更好" | 切太细掉 XGMI 带宽 + 同步开销,且本地段已填满等待。最优在中间(autotune 甜点) |
| "512 = 4096/8 已经切好,为何再切 2 片" | 512/8=8 是**计算尺**(行 tile),2 片是**通信尺**(chunk),两把独立的尺子 |

## 一句话总纲

> 每卡 = 一个独立小 GEMM `[M,K] @ [N,K].T`,**只有 M 是 8 个 rank allgather 拼出来的**,N/K 都是本地尺寸,weight 从不通信。
> 一个 kernel 里 `7×SEND_CTA` 个通信 CTA(push input)+ `grid_m×grid_n` 个计算 CTA(一 block 一个 64×64 格子);1/8 行段本地不等、7/8 等对应 rank 的 flag。
> 同一批输入行被**两把尺子**量:计算尺(`BLOCK_M`,谁来算)+ 通信尺(`SPLIT_BLOCK`,分几次到/几盏灯),后者是让计算早开始、把通信藏起来的甜点参数。
